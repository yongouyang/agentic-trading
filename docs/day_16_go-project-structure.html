Go Quant Project Structure & Module Design

From a single script to a maintainable, extensible quant system. (从一个脚本，走向可维护、可扩展的量化系统。) Good project structure is the starting point for long-term stable iteration.

1Project Directory Structure

Clear directory structure is the foundation of a maintainable, extensible quant system.

structureDirectory layout

quant/ ├── cmd/ │ └── backtest/ │ └── main.go # backtest entry point ├── internal/ │ ├── market/ # market data (K-lines, etc.) │ ├── indicator/ # technical indicators (MA, vol) │ ├── strategy/ # trading strategies (signals) │ ├── portfolio/ # portfolio (account, positions) │ ├── broker/ # trade execution (simulated) │ ├── risk/ # risk management (position, rules) │ └── backtest/ # backtest engine (orchestrator) ├── data/ # CSV data, configs, results ├── go.mod # Go module file └── README.md # project docs

Design principles (目录设计要点)

  • Modular split (模块化拆分) — by responsibility, high cohesion, low coupling
  • Clear boundaries (清晰职责边界) — each module only cares about its own job, interacts via interfaces
  • Easy to extend (便于扩展) — adding strategies/indicators/rules has minimal impact
  • Easy to maintain (易于维护) — clear structure aids debugging, testing, and iteration
  • Security (安全可控) — internal/ restricts imports, protecting core code from misuse

2Why Modular Monolith, Not Microservices?

In the early stage, a modular monolith is the more pragmatic choice for quant backtesting.

✓ Modular Monolith (current choice)

  • Low call cost, high performance — in-process function calls, no network overhead; faster backtesting
  • Simple development, efficient iteration — one codebase, unified build/run; changes validated quickly
  • Easier data consistency — shared memory, no distributed transactions needed
  • Low deployment cost — single binary, simple environment; ideal for individuals/small teams
  • Better fit for backtesting — compute-intensive tasks benefit from in-process collaboration

✗ Microservices (not yet)

  • Network overhead — inter-service calls slow backtesting significantly
  • High deployment complexity — multiple services, containers, configs, dependencies
  • Hard data consistency — needs distributed transactions, idempotency, etc.
  • High ops cost — requires monitoring, logging, tracing, service discovery
  • Premature complexity — increases system complexity, slows iteration when core logic isn't stable
When to consider splitting? Team grows → modules stabilize → scale demands independent scaling → ops maturity. Until then: get the system right before making it complex. (先把系统做"正确"，比做"复杂"的架构更重要！)

3Seven Core Modules — Each Does Its Own Job

A complete quant system needs multiple modules collaborating to turn trading ideas into executable strategies.

1

market (行情)

Load historical data (K-lines, volume, etc.). Provide unified data interface. Data alignment, cleaning, caching.

2

indicator (指标)

Compute technical indicators (MA, RSI, volatility, etc.). Incremental updates. Result caching.

3

strategy (策略)

Receive indicator data. Generate trade signals (buy / sell / hold). Configurable parameters.

4

risk (风控)

Position control (single/total limits). Stop-loss/take-profit. Portfolio risk monitoring (drawdown, vol).

5

broker (成交)

Receive orders. Simulate matching (open/close/slippage fills). Generate fill reports.

6

portfolio (账户)

Update positions and cash. Calculate equity, P&L, returns. Record account history.

7

backtest (回测引擎)

Event-driven or bar-by-bar simulation. Manage module execution order. Output results & statistics.

The backtest engine loops through each time step (T0 → T1 → T2 → … → Tn), executing this pipeline at each bar. Everything is data-driven, reproducible, and traceable.

💡 Summary: Market provides data → Indicator computes results → Strategy produces signals → Risk decides feasibility → Broker simulates execution → Portfolio updates state. All orchestrated by the backtest engine into a complete closed loop. (好的系统不是写一堆 if/else，而是让每个模块只做自己的事！)

4Go's internal/ Directory — Import Boundaries

internal is Go's built-in mechanism for defining module boundaries — restricting who can import your packages.

goHow internal works

Packages inside internal/ can only be imported by code rooted at the parent of internal. External projects cannot import them.

// ✓ ALLOWED: within parent tree
// File: quant/cmd/backtest/main.go
import (
    "quant/internal/strategy"  // ✓
    "quant/internal/indicator" // ✓
)
// ✗ FORBIDDEN: external project
// File: other-project/main.go
import (
    "quant/internal/strategy" // ✗ compile error!
)

Benefits

  • Protect internals — prevent external dependency on implementation details
  • Clear module boundaries — signals "these are internal, don't reference externally"
  • Reduce coupling — fewer misuses, easier to refactor
  • Engineering best practice — standard for large Go projects
💡 Put public/reusable packages at project root or pkg/. Keep internal implementations inside internal/. Interfaces exposed at the outer layer, implementations inside.

5Dependency Inversion — Depend on Interfaces, Not Implementations

The backtest engine is the system's core — it should be stable, generic, and not depend on any specific strategy.

✗ Wrong: backtest depends on concrete strategy

Backtest directly creates MAStrategy. To switch to trend/momentum strategy, you must modify Backtest code — risky, not extensible.

✓ Right: backtest depends on Strategy interface

Backtest only depends on the Strategy interface. New strategies just implement the interface — no Backtest changes needed. Follows the Open/Closed Principle.

goInterface-based design (Go code)

// strategy/interface.go
type Strategy interface {
    GenerateSignal(data MarketData) Signal
    Name() string
}

type Signal struct {
    Action string  // "BUY","SELL","HOLD"
    Price  float64
}
// strategy/ma_strategy.go
type MAStrategy struct {
    ShortPeriod int
    LongPeriod  int
}
func (m *MAStrategy) GenerateSignal(
    data MarketData) Signal {
    // ... MA calculation logic
}
func (m *MAStrategy) Name() string {
    return "MA Strategy"
}
// backtest/backtest.go
type Backtest struct {
    strategy Strategy    // depends on interface!
    data     MarketData
}

func NewBacktest(s Strategy, d MarketData) *Backtest {
    return &Backtest{strategy: s, data: d}
}

func (b *Backtest) Run() Result {
    // use b.strategy to generate signals
    // and run the backtest
}
// main.go — runtime composition (DI)
strategy := strategy.NewMAStrategy(5, 20)
bt := backtest.NewBacktest(strategy, data)
result := bt.Run()
💡 The backtest engine is the system's core — keep it stable and generic. Strategies can be swapped endlessly without modifying the engine. Interfaces make the system extensible, testable, and maintainable.

6Unit Testing — The Quality Foundation

Good tests = fewer bugs + faster refactoring + more confident iteration. (好的测试 = 更少的BUG + 更快的重构 + 更安心的迭代。)

testingWhat to test in a backtest system

PriorityAreaWhat to verify
1Indicator calculationsMA, RSI, ATR values are mathematically correct
2Signal generationStrategy produces correct buy/sell signals under various market conditions
3Order & matching logicOpening/closing positions, slippage, fee calculations
4Backtest result statsReturns, max drawdown, Sharpe, win rate, P/L ratio

Test pyramid (测试金字塔)

E2E Tests
few · slow · high value
Integration Tests
moderate count
Unit Tests
many · fast · high coverage

Go test example

// ma/ma_test.go
func TestSMA(t *testing.T) {
    period := 3
    data   := []float64{1, 2, 3, 4, 5}
    want   := []float64{0, 0, 2, 3, 4}
    got    := SMA(data, period)
    if !reflect.DeepEqual(got, want) {
        t.Errorf("SMA(%v, %d) = %v, want %v", data, period, got, want)
    }
}

Good testing habits

  • Test files end with _test.go; functions start with Test
  • Use table-driven tests for covering multiple cases
  • Name tests clearly: TestSMA_NormalCase, TestSMA_EdgeCase, TestSMA_InvalidInput
  • Cover normal, boundary, and error cases
  • Keep tests simple, stable, and repeatable
  • Run quickly: go test -v ./...
★Testing isn't wasting time — it's saving countless future debugging hours. Unit tests are the quality foundation; ensure indicators are correct first, then strategies, then backtest results. Good tests let you refactor, iterate, and innovate with confidence. (测试不是浪费时间，而是节省未来调试的无数小时！)
