Sliding Window & Incremental SMA

Do you need to recalculate the entire moving average every time a new price arrives? (每来一个价格，都要重新算一遍均线吗？) The key to optimizing SMA isn't "calculating faster" — it's reusing what you already computed last time, and only updating what changed.

Source: knowledge-base/day_18 (IMG_6615–IMG_6622), "30天学习量化投资 · Day 18: 滑动窗口与增量SMA" · Extracted 2025-08-30

1The Problem with Naive SMA — O(N) Every Time

Standard SMA recalculates by iterating over the last N prices every time a new price arrives. Time complexity: O(N).

problemHow naive SMA works

①
New price arrives
→
②
Take last N prices
→
③
Sum all N values
→
④
Divide by N

Example: SMA(3) with prices [10, 11, 12]

StepWindowCalculationResult
Initial[10, 11, 12](10+11+12) / 311.00
Price 13 arrives[11, 12, 13](11+12+13) / 312.00

Every new price → re-iterate all N values → O(N) per update.

With millions of bars, multiple instruments, and multiple parameter combinations — O(N) repeated computation becomes a serious bottleneck.

2Sliding Window — Subtract Old, Add New → O(1)

Instead of recalculating from scratch, maintain the running sum and only update the two changed values. (不用重新算！)

solutionCore idea

new_sum= old_sum− oldest value+ newest value
new_SMA= new_sum÷ N

Worked example: SMA(3)

StepOld sumSubtract oldestAdd newestNew sumSMA
Initial [10,11,12]33——3311.00
13 arrives33−10+133612.00
14 arrives36−11+143913.00

Each update: exactly 2 arithmetic operations (one subtraction, one addition) → O(1).

Complexity comparison

MethodPer-update opsComplexity1,000,000 updates (N=100)
Naive SMA (re-iterate)N additionsO(N)~100 million additions
Incremental SMA (sliding window)2 operationsO(1)~2 million operations
💡 One order of magnitude reduction in complexity = one order of magnitude improvement in performance. The bigger the data, the more instruments, and the more parameters — the more dramatic the advantage. (复杂度降一阶，性能提升一个数量级！)

3Circular Buffer — Fixed Memory, In-Place Overwrite

Use a fixed-size array with a write pointer that wraps around. New data overwrites the oldest data. No allocation, no copying.

structureHow it works

A circular buffer (环形缓冲区) uses a fixed-size array of length N plus a write pointer (index). When new data arrives, it overwrites the oldest value at the current index, then advances the pointer modulo N.

Physical order is scrambled — but the 3 values in the window are always the latest 3. Sum is always correct. SMA = sum / N.

Go struct design

type SMA struct {
    period int       // window size N
    window []float64 // circular buffer, len = N
    sum    float64   // running sum within window
    index  int       // next write position
    count  int       // elements written so far (≤ N)
}

Update() — O(1) core steps

func (s *SMA) Update(value float64) float64 {
    old := s.window[s.index]     // ① get oldest value
    s.sum -= old                 // ② subtract oldest
    s.window[s.index] = value    // ③ overwrite with new
    s.sum += value               // ④ add new value
    s.index = (s.index+1) % s.period // ⑤ advance pointer (wrap)
    if s.count < s.period {
        s.count++                // ⑥ track valid elements
    }
    return s.sum / float64(s.count)
}

Why not append(window[1:], value)?

append approach

  • Element shifting — moves N−1 elements each time
  • Array reallocation — capacity overflow triggers copy
  • Memory allocation — frequent alloc/dealloc
  • GC pressure — many temporary objects
  • Performance jitter — worse with larger data

Circular buffer

  • In-place overwrite — only modifies one position
  • Fixed memory — allocated once, reused forever
  • No allocation — almost zero temporary objects
  • Low GC pressure — fewer garbage objects
  • Stable performance — O(1) with minimal variance
💡 The circular buffer isn't "showing off" — it ensures the quant system remains stable, controllable, and efficient during long-running, high-frequency, large-scale computation. (环形缓冲区是为了让量化系统在长时间、高频率、大规模运行时依然稳定、可控、高效！)

4Reset & Reuse

A good indicator implementation must be resettable and reusable.

designReset() clears state for reuse

func (s *SMA) Reset() {
    s.sum   = 0
    s.index = 0
    s.count = 0
    // window doesn't need clearing — will be overwritten
}

Use cases for Reset

Re-running data

Same indicator instance, new dataset.

Unit testing

Clean state between test cases.

Parameter backtesting

One SMA instance, many parameter runs.

Indicator reuse

Same instance across different instruments.

5Don't Prematurely Unify the Indicator Interface

Different indicators have very different inputs and outputs. Satisfy real needs first, then abstract commonalities later.

designInput/output diversity across indicators

IndicatorInputOutput
SMAClose1 value (SMA)
ATRHigh, Low, Close1 value (ATR)
MACDClose3 values (DIF, DEA, Histogram)
Bollinger BandsClose3 values (Upper, Mid, Lower)

✗ Premature unification

type Indicator interface {
    Update(bar Bar) // all take Bar?
    Values() map[string]float64
    Reset()
}
  • Forces unnecessary input parameters
  • Unnatural output structure
  • Sacrifices usability and performance

✓ Implement first, abstract later

// SMA: natural, clean, performant
type SMA struct { ... }
func (s *SMA) Update(v float64) float64
func (s *SMA) Value() (float64, bool)
func (s *SMA) Reset()
  • Each indicator only cares about its own I/O
  • API is concise, intuitive, performant
  • Not constrained by premature abstractions
💡 Abstraction should emerge from real-world commonalities, not from imagined uniformity. Let each indicator run naturally in real scenarios first, then extract truly valuable common patterns from practice. (抽象应该来自于真实世界的共性，而不是来自我们想象中的整齐划一。)

6Golden Cross Is an Edge Trigger, Not a Level!

The signal is not "short MA > long MA" — it's the moment of transition from "below" to "above". (金叉不是短均线>长均线，而是边沿触发！)

signalLevel trigger vs Edge trigger

✗ Level trigger (continuous)

"Whenever short MA > long MA → BUY"

Result: BUY signal fires every bar while short MA stays above long MA — massive duplicate signals!

✓ Edge trigger (one-shot)

"Only when short MA crosses from ≤ to > long MA → BUY"

Result: BUY signal fires exactly once at the crossover moment.

Crossover conditions

SignalYesterdayTodayCondition
Golden cross (BUY)short MA ≤ long MAshort MA > long MACrossed upward at this bar
Death cross (SELL)short MA ≥ long MAshort MA < long MACrossed downward at this bar

State machine to prevent duplicate signals

const (
    IN_DOWN State = iota // short MA ≤ long MA (waiting for golden cross)
    IN_UP                // short MA > long MA (waiting for death cross)
)

type DualMAStrategy struct {
    fast, slow *SMA
    state      State
}

func (s *DualMAStrategy) OnBar(bar Bar) []Signal {
    prevFast, prevSlow := s.fast.Value(), s.slow.Value()
    s.fast.Update(bar.Close)
    s.slow.Update(bar.Close)
    fast, slow := s.fast.Value(), s.slow.Value()

    var sigs []Signal
    switch s.state {
    case IN_DOWN:
        if prevFast <= prevSlow && fast > slow {
            sigs = append(sigs, NewSignal(BUY, bar.Time))
            s.state = IN_UP
        }
    case IN_UP:
        if prevFast >= prevSlow && fast < slow {
            sigs = append(sigs, NewSignal(SELL, bar.Time))
            s.state = IN_DOWN
        }
    }
    return sigs
}
★We care about the moment of change, not the current state. "Now above" is not a signal; "just crossed above" is the signal. (我们关心的不是现在在不在上方，而是这一刻发生了什么变化！)

State machines effectively prevent duplicate signals, ensuring correct trading logic.
