Quant Trading System — Core Building Blocks

Break a complex trading system into modules with clear responsibilities, each doing one thing, collaborating through stable interfaces. (把复杂的交易系统，拆成职责清晰的模块，各司其职，协同工作。)

1Why Split Into Modules?

Splitting a system into single-responsibility modules makes it clearer, more stable, and more extensible.

"One person can walk fast; a group can walk far. One module can be written fast; only a well-structured system goes far."
(一个人可以走得很快，一群人可以走得很远；一个模块可以写得很快，一套系统才能走得很远。)

✗ If you don't modularize (Monolith — not recommended)

  • Severe code coupling — market data, indicators, trading and account logic mixed together; changing one place can break everything.
  • Hard to debug — when one part fails, locating the problem is painful.
  • Hard to test — cannot unit-test indicators, strategies, or risk rules in isolation.
  • Hard to extend — swapping a strategy or adding risk control requires rewriting the whole system.

✓ Benefits of modularization (recommended)

  • Single responsibility — each module does one thing; code is easier to understand.
  • Low coupling, high cohesion — modules collaborate through stable interfaces, not implementation details.
  • Testable — indicators, strategies, and risk rules can be unit-tested independently.
  • Extensible — new strategies, risk rules, or instruments extend one module without touching others.
  • Reusable — indicators, risk, and the backtest framework are reused across strategies.
★Modularization is not about "looking sophisticated" — it is the prerequisite for long-term stable evolution and iteration of the system.

3Module Specifications

Responsibilities, input/output contracts, and worked examples for each building block.

data/Data / Market — the raw-material layer

  • Provides raw, clean market data: OHLCV bars, tick data, fundamentals.
  • Ensures data accuracy and completeness.
  • Does no computation and no decision-making.

indicator/Indicator — the signal-processing layer

  • Computes technical indicators from market data.
  • Does not produce trade signals (不产生交易信号).
  • Reusable by many strategies (可被多个策略复用).

Common indicators: MA (moving average), MACD, RSI, ATR, Bollinger Bands, …

💡 Output of the Indicator module = indicator value series (指标值序列, e.g. MA values, MACD values).

strategy/Strategy — the decision layer

  • Consumes indicator values and produces trade signals per its logic.
  • Signal types: buy / sell / hold (+ suggested quantity).
  • Does not manage cash or positions, does not care about fills.
💡 Output of the Strategy module = signal stream (信号流: buy / sell / hold + quantity suggestion).
Example strategy: MA golden-cross (均线多头策略) MA5 crosses above MA20 → buy (金叉)
MA5 crosses below MA20 → sell (死叉)
★Data provides the "raw material", Indicator refines it into "indicator values", Strategy turns values into "signals" — but never executes trades itself.

portfolio/Portfolio — the account ledger (账户的"账本")

  • Records all current positions and cash.
  • Updates positions, cost and equity on each fill.
  • Provides query interfaces for funds and positions.
  • Does not place orders or handle fills (decoupled from Broker).

Example: portfolio update after one fill Before: cash 100,000 · position AAPL 0 · equity 100,000
Fill: buy AAPL 100 @ 150.00, fee 15.00
After: cash = 100,000 − 150×100 − 15 = 84,985 · position AAPL 100 @ cost 150.00 · market value = 15,000 · equity = 84,985 + 15,000 = 99,985
💡 Portfolio only records and computes — it never decides whether to buy, and never handles order/fill details. It is the account's "ledger".

broker/Broker — the execution layer (交易的"执行者")

  • Receives orders (from Strategy, via Risk).
  • Checks liquidity & market conditions and attempts to match/fill.
  • Computes and deducts commission and slippage.
  • Generates fill reports and notifies Portfolio.
  • Does not care about account funds or position logic.

Example: order execution with fees & slippage Order: buy AAPL 100, limit 150.00 · market last 150.10, est. slippage 0.02, fee rate 0.03%
Fill price = 150.10 + 0.02 = 150.12 · qty 100 · fee = 150.12 × 100 × 0.03% = 4.50 · total = 15,012 + 4.50 = 15,016.50
💡 Broker cares about "how to fill", not "how the book changes afterwards". The fill report is the only source of truth (成交回报才是唯一真相).

risk/Risk — the gatekeeper (最后一道防线)

  • Checks whether an order violates risk rules.
  • Controls position size, leverage, and drawdown.
  • Protects principal against extreme situations.
  • Only orders that pass risk checks may reach the Broker.

💡 Risk is the last line of defense — an order that fails risk checks must never trade.

backtest/Backtest — the orchestrator (总控调度)

  • Loads historical data.
  • Drives all modules in time order, bar by bar.
  • Records every step's results.
  • Generates the backtest report and performance metrics.
💡 Backtest is the strategy's touchstone (试金石) — without backtesting, there is no evidence a strategy works.
Key metrics in the backtest report (回测报告关键指标):
Annualized return (年化收益率)Max drawdown (最大回撤)Sharpe ratio (夏普比率)
Win rate (胜率)Profit factor (盈亏比)Number of trades (交易次数)

Loop: load data → compute indicators → generate signals → risk check → execute → update account → next bar.

★Risk controls risk and decides "can we do it"; Backtest orchestrates and decides "how well did we do". Both are indispensable: risk control first for long-term survival; backtest validation first for long-term returns.

4Core Design Principles

A running quant system is essentially the collaboration of four roles.

Strategy

Decides what it wants to do (决定想做什么)

Generates buy / sell / hold signals from indicators and logic. Doesn't care about funds, positions, or fill details.

Focus: reading the market (判断市场)

Risk

Decides whether it's allowed (决定是否允许)

Checks risk rules and limits, controls exposure and drawdown. Only approved orders reach the Broker.

Focus: controlling risk (控制风险)

Broker

Decides how to fill (决定如何成交)

Handles execution details: slippage, commissions, volume constraints. Returns real fill results.

Focus: executing trades (执行交易)

Portfolio

Records the results (记录成交结果)

Updates account state and positions; computes cost, equity, P&L — the real data for future decisions.

Focus: managing the account (管理账户)
★These four roles each do their own job; none is dispensable. Together they form a stable, efficient, and extensible trading system.

Decoupling: collaborate through stable interfaces (低耦合协作)

✗ High coupling (not recommended)

Strategy, Data, Broker, Indicator, Portfolio and Risk all call each other directly — a tangled mesh. Any module change ripples through the others; testing and extension become painful.

✓ Low coupling (recommended)

Every module talks only to a stable interface at the center. Modules depend on interfaces, not concrete implementations — easy to test, swap, and extend.

Interface contract example (接口定义依赖)

// Strategy interface — modules communicate through interfaces, not direct calls
type Strategy interface {
    OnBar(bar market.Bar) Signal  // on each new bar, return a signal
    OnInit(ctx context.Context) error
    OnFinish()
}
  • Strategy depends only on market.Bar and Signal.
  • It doesn't care where data comes from or how it's stored.
  • It doesn't care how orders are placed or how equity is computed.
  • It only cares: given a bar, what signal should I produce?

Dependency Inversion Principle (依赖倒置原则, DIP)

High-level modules (e.g. Strategy) do not depend on low-level modules (e.g. Broker, Portfolio) — both depend on abstractions (interfaces). Example: to switch from an MA strategy to an RSI strategy — ① keep the Strategy interface unchanged → ② write a new RSIStrategy implementation → ③ plug it into Backtest. No other module changes; the new strategy is live immediately.

✗ Wrong: Strategy mutates the account directly (强耦合)

// Strategy touches the account directly
if close > upperBand {
    portfolio.Cash += price * qty
    portfolio.Position -= qty
}
  • Mixed responsibilities — strategy shouldn't care how the account updates.
  • Untestable — can't test strategy logic alone.
  • Unreusable — changing execution venue means rewriting the strategy.

✓ Right: Strategy only emits signals (解耦合)

// Strategy only produces a signal
if close > upperBand {
    return Signal{
        Type:  SignalSell,
        Price: close,
        Qty:   positionQty,
    }
}
  • Single responsibility — strategy only decides "what I want to do".
  • Low coupling — no dependency on account implementation.
  • Testable — feed data in, assert signals out.
  • Extensible — works with any account or execution venue.
★Collaborating through interfaces is the key design idea that makes a quant system maintainable, testable, and extensible. Clear design is the cornerstone of long-term stability and iteration.

Day 6 summary

  • A quant system is not one big function — it is a set of modules with clear responsibilities.
  • Strategy decides what to do, Risk decides whether it's allowed, Broker decides how to fill, Portfolio records the results.
  • Modules collaborate through stable interfaces with low coupling — that is what makes the system stable, testable, and extensible.
  • Clear responsibility boundaries are the key to a sustainable quant system.
  • The only source of truth for account state is the fill report — not your assumptions (账户状态的唯一来源是成交回报，而不是你的假设).
★Good architecture turns a strategy from an "idea" into an "executable system" — the foundation for the agentic layer to build upon.
